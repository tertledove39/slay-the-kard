- 问题：多个 UI 用 `TaskCompletionSource` 无限等待按钮；节点提前退出、场景切换或选择数量大于可选项时没有统一取消路径。
- 建议：在 `_ExitTree()` 取消 TCS；校验 `pickCount`；统一弹层运行器管理创建、取消和释放。
- 验收：所有弹层在确认、取消、节点释放和场景切换下都能结束任务并清理。

## 5. 第三优先级：影响代码耦合性

### D-01 拆分 `BattleStateManager` 的全局可变状态

- 状态：`[ ]`
- 证据：`bin/CardRestoration.cs:10-293`。
- 问题：一个静态类同时承担战役、资源点、统计、区域、卡组、配置缓存、商店随机、槽位和 UI 创建；公开可变集合允许任何场景越过业务规则修改状态。
- 建议：拆为 `CampaignState`、`DeckRepository`、`ContentCatalog`、`StoreService`；场景依赖所需接口；集合对外只读。
- 验收：商店不能直接修改战役进度，UI 辅助不再位于状态仓库，领域服务可独立测试。

### D-02 把 WorldMap 从全局启动器改为地图控制器

- 状态：`[ ]`
- 证据：`bin/WorldMap.cs:118-146` 同时加载卡牌、卡组、事件、战斗名、区域池、商店队列并预加载场景。
- 问题：数据是否可用取决于是否先进入 WorldMap；直接调试其他场景需要另一套回退加载。
- 建议：建立 autoload Bootstrap/ContentRepository，在应用启动时一次验证并加载；WorldMap 只呈现区域。
- 验收：任意场景可独立启动并得到同一份验证后的数据，不再复制 card.ini 解析。

### D-03 分离 UI、领域状态和资源加载

- 状态：`[ ]`
- 证据：`Store.cs`、`EventScene.cs`、`PostBattleReward.cs` 直接修改全局状态；`cardBase_` 同时是视图、数据和战斗状态；WorldMap 直接解析 INI。
- 问题：业务规则无法脱离 Godot 节点测试，UI 测试必须构造全局状态。
- 建议：使用纯 C# 领域对象计算购买、奖励、事件和战斗结果；Godot 节点只负责输入和显示。
- 验收：资源点、购买、卡组替换和区域推进可在无场景树测试中运行。

### D-04 集中管理场景、节点与配置路径

- 状态：`[ ]`
- 证据：卡牌、世界地图、战场、开始菜单等 `res://` 字符串散落在多个类，节点路径也直接写在业务代码中。
- 问题：资源重命名需要全局文本搜索，编译器无法验证字符串引用。
- 建议：场景路径集中到只读 Catalog；常用节点使用 `[Export]` 或场景唯一名；配置路径由 ContentRepository 管理。
- 验收：重命名单个资源只修改一个权威位置，启动验证能发现缺失资源。

## 6. 第四优先级：影响代码可扩展性

### E-01 将效果解释器改为指令注册表

- 状态：`[ ]`
- 证据：`ParseAndExecuteEffect()` 超过千行，通过大量独立 `if` 与正则判断指令。
- 问题：新增指令要修改核心巨型函数、补全、变量替换和文档；相似参数解析重复，容易多分支命中或漏 await。
- 建议：定义 tokenizer/AST，用 `Dictionary<string, IEffectCommand>` 注册命令；统一参数、目标和错误诊断，保留兼容层逐条迁移。
- 验收：新增效果只需新增命令类和注册，不修改解释器主循环。

### E-02 将 Trait 元数据改为单一注册表

- 状态：`[ ]`
- 证据：`docs/NOTICE.md` 明确新增 Trait 要同步枚举、状态、描述、图标、颜色、attribute、控制台等至少八处。
- 问题：扩展点分散，遗漏任一位置就产生部分可用的 Trait。
- 建议：建立 `TraitDefinition` 注册表，集中名称、图标、描述、颜色、钩子和状态工厂；状态型 Trait 使用策略对象。
- 验收：新增 Trait 只增加一个定义和必要行为，UI 与解析自动读取元数据。

### E-03 为所有 INI 建立显式 schema 与交叉引用验证

- 状态：`[ ]`
- 证据：card、enemyTurn、event、AreaPool 由各场景自行读取，缺失字段多为默认值或运行时错误。
- 问题：无法在启动前统一发现重复 ID、未知 key、错误前缀、缺少引用和数量不一致。
- 建议：为 Card、Event、Battle、Area 定义 DTO 和 validator；加载阶段输出聚合诊断；长期可迁移到支持类型验证的格式。
- 验收：内容错误在进入菜单前一次性报告，运行期间不再因格式问题崩溃。

### E-04 建立分层测试体系，不只匹配源码字符串

- 状态：`[ ]`
- 证据：现有 Python 脚本大量通过正则和源码片段断言实现细节；本轮有脚本因重构或文件删除失败，却没有执行对应游戏行为。
- 问题：测试可能因无关格式变化误报，也可能在真实逻辑错误时继续通过。
- 建议：保留少量静态资源检查；纯 C# 领域层使用 xUnit/NUnit；Godot 场景使用可运行的集成测试；覆盖区域点击、事件、回合、购买和奖励。
- 验收：核心规则由行为断言覆盖，重命名私有函数不会导致测试失败，错误结果一定能被捕获。

## 7. 推荐实施顺序

1. 先修 C-01 至 C-08，并为每项补行为测试，消除崩溃、状态污染、重复结算与无限循环。
2. 再修 C-09 至 C-15，使购买、奖励、内容配置和测试基线可信。
